# tikz2html: notes for working on the code

tikz2html converts a LaTeX document with many TikZ(iT) figures to html. make4ht/tex4ht converts the text. Every
equation (or other block) that contains a TikZ figure is compiled separately to an svg with latex + dvisvgm, and
is put in the html with an `<object>`/`<img>`. User documentation is in `README.md`. This file explains how the
code works, and how to change it.

## Repository layout

| Path | Contents |

| `tikz2html/` | The Python package (no dependencies outside the standard library; Python 3.9+) |
| `tests/` | Unit tests and end-to-end tests (`python -m unittest discover tests`) |

| `examples/article/` | A paper whose configuration files were generated by `--init` and not edited; regenerate them with `python -m tikz2html --init examples/article/paper.tex --overwrite` after changing `init.py` |

## Modules

| Module | Responsibility |
|---|---|
| `discover.py` | Analysing a LaTeX project: following `\input`/`\include`/`\subfile`/`\import` (`find_includes`), local packages, bibliography, images, `\excludecomment`, and the macros/environments that draw TikZ with their argument specs (`macro_definitions`, `find_tikz_definitions`, iterated to a fixpoint so macros that use such macros count too) |
| `init.py` | `--init`: writes `html_config.json`, `svgbase.tex` (the document's own preamble wrapped in the svg template) and `tikz2html.cfg` from the result of `discover.py` |
| `config.py` | `Config` dataclass loaded from the JSON file (all keys have defaults), conversion of legacy formats (`normalize`), the default html templates (`DEFAULT_HTML_TEMPLATES`), `scan_config` |
| `latex_scan.py` | Comment stripping, the tokenizer, argument/brace matching, finding the *blocks*, equation numbers/labels/tags, naming blocks (`assign_ids`). Pure functions, no I/O |
| `svg_build.py` | `SvgJob` (one per distinct svg), the svg template (`render_tex`), the cache, parallel latex + dvisvgm, `svg_info` (size, baseline depth, whether it has links) |
| `html_build.py` | The placeholders that replace the blocks, html `Fragments`, the generated tex4ht `.cfg` and make4ht `.mk4`, running make4ht, copying files |
| `svg_links.py` | Parsing the tex4ht `.aux`, finding which html file has which anchor, rewriting the reference markers in the svgs into links |
| `clean.py` | `--clean`: finds the files needed to view the html by following references from the main page (html attributes, css `url()`, links in svgs), and deletes the rest of the html folder's own files and of the svg folder. It never touches other subfolders, and refuses to run if the html folder isn't a proper subfolder of the project, or if the main page is missing. If you add a new kind of output file that is only reached via javascript, add it to `clean_keep` or teach `references()` about it. |
| `pipeline.py` | `load_sources` (read, preprocess, scan all files, assign ids) and `Pipeline.run`, which runs the steps in order |
| `cli.py`, `__main__.py` | Command line options, printing errors and warnings, exit codes |
| `errors.py` | `Tikz2HtmlError` and `require_program`. See "Errors" below |

Tests: `test_latex_scan.py` covers all the ways a figure can appear in all the environments, `test_html_build.py`
the placeholders and the config, `test_svg.py` the template, the cache and the links, `test_init.py` the discovery
and `--init`, `test_errors.py` the error handling, `test_clean.py` `--clean`, and `test_end_to_end.py` runs the
real tools on a small document and on both examples. The end-to-end tests take about a minute; set
`TIKZ2HTML_SKIP_SLOW=1` to skip them.

## The pipeline (`Pipeline.run`)

1. **Scan** all source files (`load_sources`). Each file is preprocessed: comments are stripped (`strip_comments`)
   and the `preprocess_replacements` are applied. It is then scanned into `Block`s plus *skipped* spans (the
   `skip_environments`). `Block.start/end` are offsets into this **preprocessed** text, not the original file.
   All files are always scanned, even with `--only`/`--files`, so that the ids stay the same.
2. **Svgs, first pass.** `collect_jobs` makes one `SvgJob` per distinct id. `SvgBuilder.build` renders the tex
   from the template, computes the cache key, and compiles what is not cached. References use the labels in the
   `.aux` of the *previous* html run.
3. **Html.** For each block, `placeholder` produces the LaTeX that replaces it. The html it needs goes into
   `Fragments`. The rewritten tex files go to the html folder, together with `<main>-tikz2html-html.tex` (the
   fragments), `<main>-tikz2html.cfg` (the user's cfg plus our definitions) and `<main>-tikz2html.mk4` (latex,
   bibtex, latex, latex). Then make4ht runs in the html folder.
4. **Svgs, second pass.** The same build again. It only recompiles svgs whose referenced labels got a different
   value in the new `.aux` (the cache stores the values the svg was built with). On a first run this fixes all
   the `??`s.
5. **Links.** `write_linked_svgs` copies each svg from the cache to `<svg folder>/<id>.svg`, rewriting the
   reference markers into `<a href="../file.html#anchor">`.

## Concepts and invariants

**Blocks** (`latex_scan.py`). A *trigger* is a macro in `tikz_macros` or an environment in `tikz_environments`.
The scanner walks the token stream (`tokenize`) and handles three cases:
* A `math_environments` entry (`equation`, `align*`, `center`, ...), or `\[`, `\(`, `$`, `$$`. If it contains a
  trigger anywhere inside, the **whole** environment is one block. It is never split, and the scanner does not
  look inside it further.
* A trigger outside of such an environment is a block on its own. Its extent comes from the argument spec in
  `tikz_macros` (`parse_arguments`, xparse-like: `m`, `o`, `s`). Its kind is `standalone_kinds.get(name, "inline")`.
* Everything else (`figure`, `itemize`, `theorem`, tables, ...) is transparent: the scanner continues inside it.

Kinds: `display` (math display, gets equation numbers), `inline` (an image in the text), `block` (a centered
object, e.g. `center`, `\ctikzfig`).

The tokenizer treats `\\` as one token. That is what makes `\\[2pt]` not a `\[`, and `\$` not a `$`. `$` is closed
only by a `$` at the same brace depth, so `\text{$x$}` inside math works. `\verb`, verbatim environments and the
bodies of `\newcommand`/`\def` etc. (`definition_macros`) are skipped.

**Equation numbers.** `analyse_equation` splits rows at top-level `\\` (not inside braces or nested environments)
for environments with numbering `"rows"`. It creates one `EquationNumber` per numbered row (or `\tag`), and
removes `\label`, `\tag`, `\nonumber` and `\notag` from the svg source. In the html, the placeholder steps the
`equation` counter once per number, **also without a label**, so that all later numbers agree with the pdf.

**svg_source vs inner.** `svg_source` is the original block, with the numbered environment made unnumbered (`align`
becomes `align*`; the numbers are in the html) and the labels removed. `inner` is without the delimiters. It is
used for `content_hash`: blocks with the same content share one svg, even across environments, so that the same
figure is compiled only once (`dedupe_aliases` makes `\ctikzfig{x}` equal to `\tikzfig{x}`). When a shared svg is
used inline somewhere, it is compiled from the inline occurrence, because only then is its baseline right.

**Ids** (`assign_ids`) are the svg file names: the first label, else the first figure, else a macro argument,
else the macro or environment name. Different content with the same name gets `-1`, `-2`, ... Names are compared
case-insensitively, because file names are case-insensitive on Windows and macOS. Ids depend on the order of the
blocks in the whole document. That is fine: the cache is keyed by content, not by id.

**Compiling svgs** (`svg_build.py`). LaTeX runs with the project folder (the folder of the config) as its working
directory, with `-output-directory=<svg folder>/.build`. It has to: TikZiT's `\tikzfig` reads
`./figures/<name>.tikz` relative to the working directory. The template gets:
* `CONTENT_HERE` replaced by `\begin{preview}<svg_source>\end{preview}`. The preview package with `tightpage`
  crops the svg, and dvisvgm uses its data, so the viewBox origin is on the baseline. `svg_metrics` reads the
  depth from the viewBox, and inline images get `vertical-align: -depth`.
* `MAIN_FILE` replaced by the path of the html run's `.aux` (for `\externaldocument` from `xr`).
* `AUX_COMPAT` plus `svg_preamble_extra` inserted before `\begin{document}`. tex4ht's `.aux` contains
  `\rEfLiNK{anchor}{\csname :autoref\endcsname{equation}1.1}`, which needs these definitions.

Placeholders are not replaced on comment lines (`replace_outside_comments`). Failures and compilations with errors
keep their `.tex` and `.log` in `<svg folder>/_failed/`.

**Cache.** The cache lives in `<svg folder>/.cache/<key>.svg`, with a `<key>.json` next to it. The key is a hash of
the rendered tex, the `.tikz` files used, the `svg_dependencies` and the dvisvgm command. The json records the
labels that the compiled svg references (found from its markers) with the values they had. The entry is invalid
when one of these values changes. Never put something that varies between runs (like dates or absolute temp
paths) into the rendered tex, or nothing will ever be cached.

**Placeholders and fragments** (`html_build.py`). This is the most delicate part:
* The placeholders in the tex for make4ht only contain **keys**, never html:
  `\TikzSvgHtml{inline:ket0}`, `\TikzSvgDisplay{display:eq-a:before}{\TikzSvgEq{eq:a}}{display:eq-a:after}`.
  The html for each key is defined in the fragments file with `\TikzSvgDefine{key}{escaped html}`. The reason:
  a figure inside a `\caption` or `\section` is also written to the `.lof`/`.toc`, and escaped html characters
  (`%` in particular) break those files and with them the whole run.
* `hcode_escape` escapes html for `\HCode`. `\HCode` writes **everything** literally, including `{}`. So the
  escape macros are terminated by a space (`\TikzSvgPercent `), which TeX swallows when reading, not by `{}`.
  tex4ht turns `&` in attributes into `&amp;`, so don't put entities in templates.
* `\TikzSvgDisplay` ends the paragraph (`\ifvmode\IgnorePar\fi\EndP`), writes the html, and starts a new
  paragraph. The text after it gets class `indent`, like after a real tex4ht display.
* Numbers: `\TikzSvgEq{label}` does `\refstepcounter{equation}` and `\label`. tex4ht then emits the anchor
  `<a id='x..r..'>`, and `\ref` from anywhere (also other html files) links to it. `\TikzSvgTag{tag}{label}`
  redefines `\theequation` inside a group around the `\refstepcounter`, so the label gets the tag as its value,
  and then undoes the step. Setting `\@currentlabel` instead gives an anchor name that doesn't match.
* `center` blocks keep a real `\begin{center}...\end{center}` around the html, so tex4ht produces its usual
  `<div class='center'>`.

**Sizes.** Every svg gets explicit `width`/`height` attributes: the viewBox in pt × 4/3 to get px, × `svg_scale`
or `inline_svg_scale`. Don't scale with a css `transform`, and don't use a negative `z-index`. Either makes the
diagram overlap the text or be covered by it, and then the links inside it can't be clicked. Links work only
with `<object>`, so inline svgs that contain links use the `inline_linked` template.

**Links** (`svg_links.py`). The svg template wraps `\eqref`/`\ref`/`\hyperref` in
`\special{dvisvgm:raw <eqref>label}...\special{dvisvgm:raw </eqref>}`. `link_svg` turns these markers into
`<a target="_parent" href="../file#anchor" data-info="label">`. The anchor comes from `\rEfLiNK{anchor}` in the
tex4ht `.aux`, and the file from a scan of all html files for `id='anchor'`. `link_svg` is idempotent: it also
rewrites existing `<a ... data-info=...>`. Two pitfalls, both found the hard way:
* Markers nest: amsmath's `\eqref` calls `\ref`, so an `\eqref` gives `<eqref>x ... <ref>x ... </ref></eqref>`.
  Browsers don't draw the contents of a link inside a link (the equation number disappears), so `link_svg` only
  makes the outermost marker a link.
* The template must wrap the reference macros in the `begindocument/end` hook. hyperref redefines `\ref` at the
  start of the document, which silently undoes a wrapper defined in the preamble; and a wrapper in plain
  `\AtBeginDocument` can run before hyperref's own code.

**tex4ht and make4ht facts that the design depends on:**
* tex4ht loses `_`/`^` in macros that are defined in the preamble and used in math. Html versions of such macros
  must be defined after `\begin{document}` (see `main_html.tex` in the book). `\HCode{<msub>...}` can emit
  MathML directly.
* The cfg must have a `\begin{document}`; our definitions are inserted just before it. Css is added with
  `\Configure{AddCss}`, javascript with `\Configure{@HEAD}` (deferred scripts), extra html with `\Configure{@/BODY}`.
* make4ht runs in the html folder with `TEXINPUTS=.;<project>;` (see `tex_env`). The current folder comes first,
  so the rewritten chapter files win over the originals. But a **stale** copy of a preamble file in the html
  folder also wins over the original; that is why `files_to_copy` exists and is copied on every run.
* The tex4ht split level counts parts as level 1 in the book class: `next,2` splits at chapters.

## Errors

The conventions, so that users get a clear message instead of a Python traceback:
* **The conversion can't continue** (bad configuration, a missing file, a missing program, a scan error, no html
  produced): raise `Tikz2HtmlError` with a message that says what is wrong and how to fix it. Mention the
  configuration key involved. `cli.main` prints it as one line, `tikz2html: error: ...`, with exit code 2.
  Any other exception is a bug, and shows a traceback.
* **Part of the result is wrong** (an svg failed, a figure is missing, make4ht reported errors): add a line to
  `Pipeline.report` and continue. Set `Pipeline.failed` when the output is incomplete (exit code 1); don't set it
  for warnings like svgs compiled with LaTeX errors (exit code 0).
* **Possibly a mistake** (an unknown configuration key, `--only` matching nothing): add it to `config.warnings`,
  or log a line starting with `Warning:`.
* Check external programs with `require_program` just before the step that needs them, not at the start. Then
  `--list`, `--clean` and `--skip-svgs` work without the programs that those steps don't need.
* `SvgBuilder.build` stops with an error when the first `STOP_AFTER_FAILURES` (8) svgs all fail. Otherwise a
  broken template would give over a thousand identical failures for a book.
* The errors of an svg compilation are stored in the cache metadata. They are reported again on later runs, when
  the svg comes from the cache.

`tests/test_errors.py` covers these cases, mostly without needing TeX: a program that exists but produces
nothing is simulated with `[sys.executable, "-c", "pass"]`.

## How to customize

* **Another macro that draws TikZ:** add it to `tikz_macros` with its argument spec. If the svg template doesn't
  know it, `\input` its definition there or use `svg_preamble_extra`.
* **Another environment that must become one svg** (e.g. `dmath`, or a custom diagram environment): add it to
  `math_environments` as `[kind, numbering]`. Use `tikz_environments` instead when the environment itself draws
  TikZ and should be a trigger.
* **Different html** for the diagrams: use `html_templates` in the config; see `DEFAULT_HTML_TEMPLATES` for the
  keys and fields. To add a field, compute it in `placeholder` (or in `size_values`, for size-related fields),
  and extend `svg_info` if it needs information from the svg file.
* **A new kind of block:** add the kind to `placeholder` (`html_build.py`), and make the scanner produce it
  (through `math_environments` or `standalone_kinds`). Keep the rule that placeholders only contain keys.
* **Numbering with another counter, or per section:** `\TikzSvgEq` uses the `equation` counter; change it in
  `TEX4HT_DEFINITIONS`. Make the scanner decide per environment if needed (the second element of the
  `math_environments` value).
* **Text substitutions** (e.g. a macro tex4ht can't handle): `preprocess_replacements`. They apply to both the
  svgs and the html. For html-only changes, redefine the macro in the document inside `\ifdefined\HCode`.
* **Another kind of reference that should become a link:** wrap it in the svg template the same way as `\eqref`.
  If the marker tag is new, add it to `RAW_REF_RE` (`svg_build.py`) and `_RAW_OPEN_RE`/`_RAW_CLOSE_RE`
  (`svg_links.py`).
* **Other tools** (e.g. `lualatex` with `dvisvgm --pdf`): `latex_cmd`, `dvisvgm_cmd`. `compile` assumes a `.dvi`
  output; adapt it for pdf.

## Working on it efficiently

Full documents are slow: about 1000 svgs take around 10 minutes, and make4ht several minutes. Test on a small set:
* `--list` prints all blocks (file:line, kind, environment, id, labels, numbers). It is instant; use it to check
  scanner changes on a real document.
* `--only "id,label,figure-*" --skip-html` (re)builds a few svgs. Look at `_failed/` for logs.
* `--files chapter --draft` runs make4ht on one chapter only, in one pass.
* `examples/book` and `examples/article` convert in about 30 and 20 seconds and cover most features. Check the
  result in a browser.
* For the scanner, add a unit test in `tests/test_latex_scan.py` first. They run in milliseconds.

Pitfalls when developing on Windows with Git Bash:
* Heredocs and `sed` mangle backslashes, which LaTeX code is full of. Write Python or TeX snippets to a file
  (with an editor tool), then run that file.
* Run tools with `stdin=subprocess.DEVNULL`. A TeX error otherwise waits for input forever, and make4ht seems to
  hang.
* If make4ht hangs or fails on a big document, find the cause by bisection with `--files`. Look for `^!` in
  `<html folder>/<main>.log`. The full make4ht output is in `<main>-make4ht.log`.
